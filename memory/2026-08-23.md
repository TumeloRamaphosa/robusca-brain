## Why studex-group.com didn't "just work"

`storage.ts` does `new Database("data.db")` — `better-sqlite3`, a native
`node-gyp` addon writing to a local file.

- **Vercel**: ephemeral, unshared function filesystem. Approving content would
  appear to work then silently revert.
- **Cloudflare Workers**: cannot load native addons *at all*. Hard isolate
  limit; `nodejs_compat` cannot fix it.

Checked current limits rather than assuming: Vercel's default function duration
is now **300s**, so the Higgsfield route's ~210s worst case actually fits. The
timeout was never the blocker — **the database is.**

Recommended split, in `os/war-room/DEPLOY.md`: `www.studex-group.com` = public
static site on Vercel (doesn't exist yet, needs building);
`warroom.studex-group.com` = the dashboard on a container host behind
**Cloudflare Access** (auth with zero application code — right answer for an
internal tool).

## The big constraint I didn't expect: Base44

`superagents.` is built on **Base44** (AI app builder, managed backend). The
marketing page is a single inlined 780KB file on Vercel, but the *product* lives
in Base44 — "Talk to Elara" links to `app.base44.com/superagent/<id>`.

**Base44 export is frontend-only.** Database and managed auth stay locked to
their platform, and exported code still calls the Base44 SDK. So "put all the
code together in one repo" is **not fully achievable** for Super Agents without
rebuilding that backend. Commercial decision, not technical. This determines
whether a monorepo is even the right target — flag it before anyone starts.

## Also worth knowing

- Cloudflare Access **only works on proxied records.** All records are
  grey-cloud, so Access would do nothing for the existing Vercel sites without
  orange-clouding them first (which adds double-CDN problems, and needs SSL mode
  Full (strict) or you get redirect loops). For the existing sites use **Vercel
  Deployment Protection** instead. Access is still right for a *new*
  `warroom.` record on a container host.
