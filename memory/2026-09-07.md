## Findings

- **Verdict: clean.** No malware, no exfiltration, no credential/env access, no backdoors, no destructive ops, no `chmod 777`. All installs go through signature-verified `apt`/`pkg`/`pip`. Both scripts pass `bash -n`.
- Four real caveats, all local/LAN trust issues rather than malice:
  1. `termux-x11 :0 -ac` disables X11 access control — any app on the phone can read the screen and inject keys.
  2. HA binds `0.0.0.0:8123` over plain HTTP and first-launch onboarding is unauthenticated — first device to reach it becomes admin.
  3. HACS installs via unpinned `wget | bash` from `get.hacs.xyz` (legitimate project, still remote code with no checksum). Recommend declining the prompt.
  4. PulseAudio TCP with `auth-anonymous=1` on loopback — local apps can reach the mic.
- Non-security: the HA script `sed`-patches `ifaddr/_posix.py` to swallow an `OSError` (Android blocks `getifaddrs()` in proot). Documented upstream, but it silences that error path venv-wide.

## Decisions Made

- **Decision:** Approve `mayukh4/linux-android` for use, conditional on a dedicated wiped phone on an isolated network segment, Termux from F-Droid (not Play Store), HACS declined, port 8123 never forwarded. → Awaiting Agent Lord sign-off.

## Second Thread — "How do we create an app and sell it"

Tumelo asked how we build an app and monetize it. Answered with a decision doc: `studex/app-build-and-sell-playbook.md`.

### Position taken

- Reframed the question. Building the app is the cheap part now; distribution is the asset. The 33 named restaurants in `deployment/studex_os/WHOLESALE_RESTAURANT_GTM.md` ARE the distribution — build for users we can already reach by name, then sell the proven thing to their peers.
- **Recommended:** wholesale reorder app for Studex Meat restaurant accounts. Weekly reorder = highest-frequency B2B habit that exists, retention is structural, pays for itself by raising AOV on an existing pipeline, and generates order data no SA premium meat supplier has.
- **Argued against** the Client App Factory in `studex/cto-playbook.md` — services business, one-off revenue, no moat, permanent support burden. Park it.
- **Argued against** a consumer Studex Meat app — Shopify already does it better, and native adds an app-store cut on our own margin for nothing.
- **Pushed back on the playbook's React Native + Expo default** for this product: ship a PWA first. No store review, no platform cut, one build covers the tablet/desktop/phone mix that restaurant back-offices actually use, and a rep can open it in a browser mid-tasting.
- **Key insight flagged:** wholesale runs on credit (7/14/30-day EFT per the tier structure), so the app must invoice against an account, NOT demand a card at checkout. Payment *tracking* matters more than payment *collection*. Get this wrong and chefs go back to WhatsApp permanently.
- **Phase 2 = the real product:** white-label the proven system to the suppliers in the GTM competitor table (Frankie Fenner, Rossouw, Angus Meat Supply, regional biltong/seafood). Est. R3,500–R12,000/month + R15,000–R40,000 setup. 20 suppliers ≈ R1.68m ARR off a build we needed anyway.
- **On ads:** worthless for phase 1 (40 named venues — a rep with a cooler box is cheaper) and weak for phase 2 (sub-500-buyer market). Save ad spend for consumer Studex Meat.
