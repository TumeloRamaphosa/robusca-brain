## Daytona — and a correction to my own earlier design

Researched Daytona. It's a much better fit than I assumed, and it **corrects something I got
wrong** in `delivery-model/02-CONTROL-PLANE-ARCHITECTURE.md`.

**What I'd said:** one persistent agent runtime per tenant.
**What's better:** ephemeral sandbox per *task* + persistent volume per tenant. Sub-90ms creation,
per-second billing, 15-minute default auto-pause.

**Cost impact:** 2 vCPU / 4 GiB / 20 GiB storage at Daytona list ($0.0504/vCPU/h, $0.0162/GiB/h,
$0.000108/GiB/h):
- Persistent 24/7 → ~$122/mo ≈ **R1,955** (39% of R5,000 revenue)
- Bursty 2h/day → ~$11.52/mo ≈ **R184** (3.7%)

That single architectural change is the whole argument.

**Key Daytona capabilities:** container/microVM isolation per sandbox with dedicated namespaces,
network segmentation preventing lateral movement, resource quotas, per-tenant network allow-lists.
**Daytona Secrets keeps plaintext credentials OUTSIDE the sandbox and substitutes at network
egress** — solves the credential vault requirement outright. Plus volumes (shared data without
breaking isolation), snapshots + declarative image builder, SSH/VS Code/web terminal for support,
SOC 2 / ISO 27001 aligned, HIPAA + GDPR, annual third-party pen testing, BYOC for enterprise.
SDKs in Python/TS/Go/Java/Ruby + REST + CLI. $24M Series A early 2026. **Startup programme: up to
$50k credits — apply immediately.**

**Architecture set:** two planes. Always-on (tenant registry, keys, memory Postgres+pgvector,
ledger, channel gateway, scheduler) on **Fly.io**; bursty execution on **Daytona**. This matches
the existing `STUDEX_OS.md` rule (Fly.io always-on, Vercel dashboards). Memory deliberately lives
in the control plane, not the sandbox — must survive sandbox deletion, and a compromised sandbox
must not read the whole Ghost.

## OpenClaw — yes, and it saves building a scheduler

Researched OpenClaw automations properly. It's a real scheduler: `at` / `every` / `cron` (with
`--tz`) / `on-exit` / `stream`. Runs **inside the Gateway process** (Gateway must be up for
schedules to fire). Jobs persist locally (SQLite; older versions `~/.openclaw/cron/jobs.json`).
Delivery to chat channel, webhook, or nowhere. Every run creates a background task record.
One-shot jobs only auto-delete on `completionStatus: "succeeded"` — failures stay disabled rather
than replaying side effects. Recurring retry backoff 30s/1m/5m/15m/60m. Webhooks + Gmail PubSub
triggers. `openclaw cron` is an alias for `openclaw automations`.

**Session targets are the useful part:** `main` (system event, can wake heartbeat), `isolated`
(fresh session — best for reports, won't clutter client chat), `current` (bounded tail),
**`session:<id>` (persistent named session, context carries across runs)** — that last one is what
makes a daily brief build on yesterday rather than starting amnesiac.

**Recommendation: author on desktop, run one Gateway per tenant on Fly.io.**

Why not desktop for production, in severity order:
1. Gateway must be running — closed lid silently kills a paying client's routines
2. **Automation mutations require `operator.admin`** — on a shared Gateway there's no way to let a
   client manage their own routines without admin over everyone's. Per-tenant Gateway scopes this
   cleanly. *This reason contains the solution.*
3. Jobs are single-instance local state — no tenant concept
4. One OpenClaw instance = one agent workspace

Cost ~R80–240/tenant/month on Fly. Painful past ~50 tenants — right trade for a pilot.

**Routines as versioned YAML specs** in `studex/routines/`, filtered by tier, synced per tenant.
That's what converts delivery labour into product. `suppress_if_empty` on watch routines — a
routine posting "no new matches" 3×/day trains the client to ignore the channel.

Starting set of 10 routines defined (morning brief, tender watch, RFQ watch, pipeline decay,
document expiry, buyer signals, price watch, content performance, weekly market sweep, **Friday
client report**). No 3-hour cadences. The Friday report is the one not to skip — it's the artefact
that justifies the subscription and doubles as the ledger extract.
